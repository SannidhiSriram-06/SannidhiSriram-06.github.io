Case Study 01 · AWS

Cloud Support & Customer Engineering Simulation

AWS support engineering sandbox simulating remote incident response via AWS Client VPN (Mutual TLS) & SSM Session Manager. Isolated network vs server faults using CloudWatch Logs Insights, executed point-in-time recoveries with AWS Backup, and produced technical KB articles.

Architecture Analyst → Client VPN (mTLS) + SSM Session Manager → private EC2 → CloudWatch Logs Insights → AWS Backup point-in-time restore

Every remote session is brokered through Client VPN and SSM — there is no public SSH. CloudWatch Logs Insights is used to prove whether an outage is a misconfigured security-group rule or an application failure, and AWS Backup rebuilds deleted records onto a replacement EC2 instance, which is then verified by hand rather than trusting the job's "success" status.

AWS Client VPN SSM Session Manager CloudWatch Logs AWS Backup EC2 IAM

Case Study 02 · Observability

Cloud Security Observability Stack on ECS Fargate

Production-style observability pipeline provisioned via Terraform. Custom linux/amd64 Prometheus image on ECS Fargate scrapes HTTP request rates & TSDB series, feeding a 3-panel Grafana dashboard with active PromQL alert rules firing on high request rates to CloudWatch log groups.

Architecture Terraform → VPC · ECS Fargate → Prometheus :9090 ─scrape→ Grafana :3000 → alert rule (rate > 0.5) → CloudWatch Logs

Terraform provisions the entire stack in ap-south-1 — VPC, subnets, security groups, ECS cluster, IAM execution/task roles — with zero EC2. A custom linux/amd64 Prometheus image built and pushed to ECR scrapes its own request and TSDB metrics into a 3-panel Grafana dashboard, and a warning-severity alert fires when the 5-minute request rate crosses 0.5.

AWS ECS Fargate Prometheus Grafana PromQL Terraform ECR

Case Study 03 · GitOps

AI Test Generator & GitOps Pipeline

FastAPI service leveraging Groq LLaMA 3.1 to convert Python source into executable pytest suites with rate limiting and input validation. Automated Jenkins CI pipeline enforces a strict 70% coverage gate, pushes immutably tagged images to AWS ECR, and triggers ArgoCD GitOps sync to Minikube Helm releases.

Architecture git push → Jenkins (pytest, 70% coverage gate) → Docker multi-stage build → ECR (BUILD_NUMBER-COMMIT_SHA) → bump image.tag in GitOps repo → ArgoCD → Kubernetes (Minikube)

Application code and deployment state live in two separate repositories. Jenkins fails the build below 70% coverage, pushes an immutably tagged image to ECR (lifecycle policy: keep last 10, scan-on-push), then commits that tag into the Helm chart's values.yaml, where an externally configured ArgoCD application reconciles it onto the cluster.

FastAPI Groq LLaMA 3.1 Jenkins Docker AWS ECR ArgoCD Kubernetes Helm

Case Study 04 · SRE

Self-Healing Microservice on AWS

Fault-tolerant containerized microservice featuring 5-layer recovery: application health checks (/actuator/health), container auto-restarts, ALB traffic isolation, and Auto Scaling Group EC2 replacement. Provisioned via Terraform with GitHub Actions CI/CD enforcing Snyk SAST/SCA security gates.

Architecture Client → ALB (health check /actuator/health every 30s) → Target Group → ASG (2–4× t3.micro, multi-AZ) → Dockerised Spring Boot on EC2

Five recovery layers stack: Actuator health endpoint, container restart-on-crash, ALB target isolation after 3 failed checks, ASG instance replacement on failed ELB health checks, and CPU target-tracking auto-scaling at 80%. GitHub Actions builds, tests and Snyk-scans the image (dependency + image); promotion to EC2 is a manual pull-and-run.

Spring Boot AWS ASG ALB Terraform Docker Snyk GitHub Actions

Case Study 05 · Azure AI

AI Patient Triage System on Azure

Cloud-native Flask application hosted on Azure App Service (Linux, Gunicorn) integrating Azure OpenAI GPT-4o for real-time symptom triage (Urgent Care, Non-Urgent, Self Care). Records every interaction in Azure Table Storage for complete auditability with zero hardcoded credentials.

Architecture User → Flask on Azure App Service (Linux B1, Gunicorn) → Azure OpenAI (GPT-4o, triage-model) → Azure Table Storage (triagelogs) → response

Compute, inference and storage are three independent managed services with no self-hosted infrastructure. The web tier stays stateless, every symptom/response pair is written to Table Storage for a queryable audit trail, and all four connection secrets are injected as App Service configuration rather than committed.

Case Study 06 · Serverless

Bookstore Serverless Architecture on AWS

Serverless microservices case study mapping Node.js REST APIs to AWS Lambda compute, API Gateway HTTP routing, and MongoDB Atlas cloud database. Includes AWS Free Tier cost optimization analysis ($0/mo for low traffic) and CloudWatch log integration.

Architecture Client (HTTPS) → API Gateway REST (GET/POST /books, Lambda proxy, CORS) → AWS Lambda (Node.js 20.x) → MongoDB Atlas (M0) → CloudWatch Logs

A service-mapping study: each part of a traditional Express app is swapped for a managed AWS equivalent — Lambda for compute, API Gateway for routing and HTTPS, Atlas for the database, CloudWatch for logs — and the whole thing sits at $0/month under the free tier for low-traffic use.
