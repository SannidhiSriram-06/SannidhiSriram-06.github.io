01 AWS, us-east-1 · Terraform

Identity Threat Detection and Response Lab

A single t3.large on AWS, built with Terraform, runs HashiCorp Vault 1.15 and a single-node Wazuh 4.7.5 SIEM in Docker Compose. Vault's AWS secrets engine issues short-lived IAM users on request. Wazuh reads the host's auth log and, through an S3 bucket, AWS CloudTrail.

I wrote five custom Wazuh rules and ran three simulations on the host: an SSH username spray, a run of unauthorised sudo commands and Vault credential requests. They produced 33 alerts, mapped to MITRE ATT&CK: T1110 for password guessing and spraying, T1548.003 for sudo abuse, and T1078.004 and T1098 for IAM user creation. Separately I checked that a Vault-issued IAM user was deleted when its 900 second lease expired and when I revoked it.

It stops short of a real attack. Everything ran from localhost on one host, and CloudTrail takes 5 to 15 minutes to arrive, so those alerts are not instant. The incident-response runbook is written, but I did not run it against the live alerts. Wazuh uses its default credentials and Vault's unseal key sits on the host, so this is a lab and not a pattern to copy.

Terraform, HashiCorp Vault, Wazuh, AWS CloudTrail, Docker Compose

  1. 02 AWS · Terraform

    Cloud Compliance and Vendor Risk Lab

    Terraform deploys four deliberately bad resources: a public S3 bucket, a security group open to SSH from anywhere, an unencrypted EBS volume and an IAM user without MFA. AWS Config and Security Hub, set to the CIS AWS Foundations Benchmark v1.4.0, evaluate them, and two EventBridge rules send failures to a Python Lambda.

    The Lambda writes each finding to S3, merges the duplicates that Config and Security Hub both report, and rebuilds a risk register as JSON and CSV. In the live run it recorded 21 findings, 17 mapped to CIS controls and 4 unmapped, each with an owner and an SLA based on severity. Alongside it, a command-line script scores a fictional vendor from a sample questionnaire and writes a report, and a small Flask dashboard shows the register and the vendor score.

    The ISO 27001 and NIST CSF mappings are my own indicative crosswalk, not an official one, and the vendor and its answers are invented. The dashboard reads a saved copy of the register, not the live S3 file.

    Terraform, AWS Config, Security Hub, EventBridge, Lambda (Python), Flask

  2. 03 AWS, us-east-1 · Terraform

    Cloud Support Simulation

    One t3.micro in the default VPC runs a small Flask app. Terraform creates the instance, its security group, IAM roles, a CloudWatch log group and a daily AWS Backup plan. I played two roles: an owner who builds it, and a support analyst with scoped, non-admin permissions (an attempt to create an access key as that user was denied).

    Ticket one, the app is down: the analyst connected through SSM Session Manager, saw the app healthy on the host while CloudWatch Logs Insights showed no requests arriving, traced it to a missing security group rule and added it back. Ticket two, my data is gone: I restored a deleted file from an AWS Backup recovery point onto a new instance. The job reported COMPLETED, but a file written seconds before the backup was missing, so I checked the restored instance directly before writing to the customer. I also set up an AWS Client VPN endpoint with mutual-TLS certificates made with Easy-RSA and reached the instance's private IP over it.

    The write-ups are two incident reports, two knowledge-base articles and a customer update. It is a simulation: one instance with a public IP in the default VPC, and SSM session logging was not turned on.

    Terraform, AWS Client VPN, SSM Session Manager, CloudWatch Logs Insights, AWS Backup

  3. 04 AWS, ap-south-1 · Terraform

    Observability Stack on ECS Fargate

    Terraform builds a VPC with two public subnets, a security group, IAM roles, an ECS cluster and a CloudWatch log group, then runs two Fargate services. Prometheus uses a custom image I built for linux/amd64 and pushed to ECR. Grafana runs the stock image.

    In Grafana I made a three-panel dashboard (total HTTP requests, request rate over 5 minutes and active time series) and an alert rule that fires when the request rate passes 0.5, evaluated every minute. Screenshots of the cluster, the Prometheus targets, the dashboard and the alert are in the repository.

    Prometheus only scrapes itself, so the dashboard shows Prometheus's own metrics and no application was monitored. Both services have public IPs, with ports 3000 and 9090 open to the internet. That is fine for a short lab and wrong for anything else.

    Terraform, ECS Fargate, Prometheus, Grafana, ECR

  4. 05 Kubernetes (Minikube) · GitOps

    AI Test Generator and GitOps Pipeline

    The service is a FastAPI app with one real endpoint. POST /generate takes up to 2,000 characters of Python, validates it, limits callers to 5 requests a minute and asks Groq's llama-3.1-8b-instant for a pytest file. The project is mostly the pipeline around it: a Jenkins job runs pytest with a 70% coverage gate, builds a multi-stage Docker image, pushes it to ECR (created with Terraform) tagged with the build number and commit, and commits that tag to a second repository that holds the Helm chart.

    Splitting the repositories is the GitOps part. Jenkins never holds cluster credentials; it only writes an image tag to Git. An Argo CD application watching the chart repository syncs it to a Minikube cluster, where the Deployment pulls from ECR with a pull secret and reads the Groq key from a Kubernetes Secret.

    The Argo CD application and the cluster were set up by hand outside the two repositories, so the repos show the chart and the CI side but not Argo CD itself.

    FastAPI, Jenkins, Docker, ECR (Terraform), Helm, Argo CD

  5. 06 AWS, us-east-1 · Terraform

    Self-Healing Java Microservice

    Terraform builds a VPC across two Availability Zones, an Application Load Balancer with a target group, and an Auto Scaling Group of 2 to 4 t3.micro instances whose user data installs Docker and runs the Spring Boot image. Recovery happens in layers: the Actuator health endpoint, a Docker health check every 30 seconds, ALB health checks that drop a target after 3 failed 30 second checks (about 90 seconds), an ASG that uses those ELB checks to replace the instance, and a target-tracking policy that adds instances at 80% CPU.

    A GitHub Actions workflow builds with Maven, runs the tests, pushes the image to Docker Hub and runs Snyk dependency and image scans. It ran green in February 2026.

    Two gaps. Snyk runs after the push, so a finding fails the run but does not stop the image being published, and deploying a new image to EC2 is manual. Runs since February fail at the Docker Hub login because the secrets are no longer set.

    Terraform, ALB and Auto Scaling, Spring Boot, GitHub Actions, Snyk

  6. 07 AWS, us-east-1 · Serverless

    Bookstore Serverless API

    A Node.js 20 Lambda handles GET and POST /books behind an API Gateway REST API on a prod stage, with CORS enabled and logs going to CloudWatch. I built it to practise mapping the parts of a bookstore API (compute, routing, storage, logging) onto serverless services. The repository keeps the deployment screenshots and an architecture write-up.

    On the Free Tier it costs nothing while idle, because Lambda and API Gateway charge per request. I deleted the AWS resources after testing.

    It is not a working bookstore yet. The handler keeps three books in an array inside the function, so a POSTed book disappears on the next cold start. I set up a MongoDB Atlas cluster and the mongodb driver is in package.json, but the code never connects to it. Wiring that in is the obvious next step.

    AWS Lambda, API Gateway, CloudWatch Logs

  7. 08 Azure · Python

    Patient Triage on Azure

    A Flask app on Azure App Service (Linux, B1 tier, Gunicorn) takes a free-text symptom description and sends it to an Azure OpenAI gpt-4o deployment. The prompt asks for Urgent Care, Non-Urgent Visit or Self Care plus a short reason, and the app shows the answer. Each symptom and result pair is written to an Azure Table Storage table called triagelogs.

    The point was the cloud wiring, not the medicine. Compute, model and storage are three managed services, and all keys come from App Service configuration, so none are in the repository. A PDF of timestamped console screenshots shows the resources and the app running before I decommissioned them.

    It is a proof of concept with no authentication, input validation, rate limiting or retries around the model call, and its answers should not be used for real medical decisions.

    Azure App Service, Azure OpenAI, Azure Table Storage, Flask

Experience

AI Intern and Cloud Deployment Lead, Infosys Springboard

Remote · February to April 2026 · AI KYC verification system

A 25-member team split into ML, web and cloud sub-teams. I led the cloud sub-team and was one of two co-leads, alongside the ML lead, coordinating all three.

In sprint 14 I took the system to AWS: the React frontend on S3 static hosting, and the Node.js API and the Flask ML service (three GNN document models) on EC2, both run under PM2. Five deployment defects came up:

Request path
The frontend called the ML service directly, bypassing the backend and breaking auth and CORS. I routed everything through one backend endpoint.
Bind address
The Node.js API listened on 127.0.0.1 only and refused outside connections. I bound it to 0.0.0.0.
CORS
The API only allowed localhost:5173, which blocked the S3-hosted frontend. I added the S3 origin.
PM2 interpreter
PM2 started the ML service with system Python, which crashed on a missing numpy. I pointed PM2 at the virtual environment's interpreter.
Bad uploads
A random non-KYC image could crash the flow. I added a "Non-KYC Document" result path end to end.
